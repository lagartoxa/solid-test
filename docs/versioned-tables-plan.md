# Plan: versioned tables (history of changes)

> Status: implemented. Differences from the original plan:
> - The history class is created in `__declare_first__` (when the mappers are configured), not when the model class is defined: foreign key columns only get their type once the referenced table exists. `app/db/models/__init__.py` calls `configure_mappers()` after importing every model.
> - History is written in `after_flush` with a Core `insert()` (not `before_flush` + `session.add`), so generated values (id, version, server defaults) are already known. `eager_defaults` is on for versioned models for the same reason. `BaseModel.id` did not need a Python-side default.
> - A hard delete is recorded with the next version (the row's version is not incremented because the row is gone).
> - No separate index on `history.id`: the unique `(id, version)` index already serves lookups by id.
> - The listener is registered in `app/db/session.py`, so it is active for every session, including `flask seed`.

## Context
We want to keep every change of a cart's status (active → checked_out / abandoned), mainly so we can **debug errors later**: when something goes wrong with a payment, we can see exactly which states a cart went through and when. The solution must be generic. Any table gets history by inheriting from `VersionedBaseModel` instead of `BaseModel`, plus a migration.

Decisions taken with the user:
- Name: `VersionedBaseModel`, next to the existing `BaseModel` ([app/db/models/base.py](../app/db/models/base.py)).
- Mechanism: SQLAlchemy session events (the SQLAlchemy "versioned history" pattern), not PostgreSQL triggers.
- History stores **what** changed and **when**, not who (consistent with the README note that per-user traceability is overkill here).
- First table to version: `carts`.

## Design

### 1. `VersionedBaseModel` ([app/db/models/base.py](../app/db/models/base.py))
```python
class Cart(VersionedBaseModel):   # was: class Cart(BaseModel)
```
- Abstract, inherits `BaseModel` (so it keeps id, timestamps, soft delete).
- Adds a `version INTEGER NOT NULL` column, set up as SQLAlchemy's `version_id_col`: 1 on insert, +1 on every update. As a bonus this gives **optimistic locking**: an update based on a stale row raises `StaleDataError` instead of silently overwriting a concurrent change.
- In `__init_subclass__`, after the class is mapped, it creates the matching **history model** automatically:
  - Table `<tablename>_history` (e.g. `carts_history`), ORM class `<ClassName>History` (e.g. `CartHistory`).
  - Columns: `history_id` (BIGINT identity, PK), a copy of every column of the original table except `created_at`/`updated_at` (types and nullability kept; no FKs, unique constraints or defaults, so history survives anything that happens to the original rows), `operation` (`insert` / `update` / `delete`), `changed_at` (TIMESTAMPTZ, `clock_timestamp()`).
  - Unique `(id, version)`, plus an index on `id`.
  - Inherits only `Base`, not `BaseModel`: history is append-only, so no soft delete and no `updated_at`.
- Small change in `BaseModel`: `id` also gets a Python-side default (`uuid.uuid4`, keeping the DB default). This way new rows already have their id before the flush, when the history snapshot is taken.

### 2. Writing history (`app/db/repositories/versioning.py`)
- One `before_flush` listener on the SQLAlchemy `Session` class, registered once.
- For each `VersionedBaseModel` instance in the flush:
  - `session.new` → snapshot with `operation=insert`, `version=1`.
  - `session.dirty` with real column changes (`session.is_modified`) → `operation=update`, `version=current+1`. A soft delete or restore is an update where `deleted_at` changed, so it shows up clearly.
  - `session.deleted` (hard delete) → `operation=delete`.
- The snapshot is added to the same session, so it is written **in the same transaction** as the change. If the change rolls back, its history rolls back too.
- The listener lives in the repositories package because it is database access (CLAUDE.md: no SQL outside repositories). It only uses the ORM (`session.add`), no SQL strings.
- Known limit: bulk statements (`session.execute(update(...))`) skip ORM events. Versioned tables must always be changed through ORM instances, which `BaseRepository` already does. This will be written in CLAUDE.md.

### 3. Reading history (`app/db/repositories/base.py`)
- `VersionedBaseRepository(BaseRepository)` adds `get_history(id) -> list[History]`, ordered by version (including versions of soft-deleted rows).
- `CartRepository` switches its base to `VersionedBaseRepository`.

### 4. Migration (new Alembic revision, autogenerated + reviewed)
- `carts.version INTEGER NOT NULL DEFAULT 1` (the server default covers existing rows).
- Create `carts_history` with its constraints and index.
- Backfill: one `insert` history row (version 1) for each existing cart, so every cart has a complete history. `INSERT … SELECT` inside the migration is allowed by the CLAUDE.md migration exception.

### 5. Effect on the payment plan
The payment flow changes the cart status in the webhook (`active → checked_out`). With `Cart` versioned, those changes are recorded automatically; the payment code doesn't need anything extra. This note will be added to [docs/payment-requirements.md](payment-requirements.md).

## README decision (to add)
> **Versioned tables.** Any table can keep a full history of its changes by inheriting from `VersionedBaseModel` instead of `BaseModel` (and generating a migration). Each insert, update, soft delete or hard delete writes a snapshot to `<table>_history` with the version, the operation and when it happened, in the same transaction as the change. `carts` is versioned so every status change is kept. **This was decided so the history can be used to debug errors later**, e.g. to see which states a cart went through around a failed payment. It records what changed and when, not who (see the traceability note in the assumptions).

## Tests (`tests/integration/test_versioning.py`)
- Creating a cart writes history version 1, `operation=insert`.
- Changing the status writes version 2 with the new status; `get_history` returns both, in order.
- A flush with no real change writes no history row.
- Soft delete and restore are recorded as updates with `deleted_at` set / cleared.
- A rollback writes no history.
- A non-versioned model (e.g. `User`) writes no history and has no `_history` table.
- Updating a stale cart (version changed by another session) raises `StaleDataError`.
- The history table has the copied columns plus `history_id`, `operation`, `changed_at`, and no FKs.
